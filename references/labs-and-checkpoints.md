# 检查点设计:lab、评测机与自查清单

本文件在设计或检查检查点时必读。所有反馈遵守 SKILL.md §1.2 锚定约束。

所有检查点遵守 SKILL.md §2.2 核心协议(交付—提交—检查):agent 在阶段开始时交付检查点,然后不再提起;学习者完成后自己提交,提交是核对的邀请;未提交而宣布进入下一阶段时提醒一次,不强制;坚持跳过则记录为学习者的主动选择(记事实,不评判)。

## strong 模式

### 1. 现成课程 lab 优先,且可跨源

成熟公开课的 lab 经过成千上万学生检验,质量远高于现写;lab 跟着阶段目标挑,不必与讲义出自同一门课。

采用纪律:

0. **唯一入口**:课程作业仓库直接放学习仓库根级 `labs/<assignment>/`;不得放到 `coursepacks/.../assignments/` 后再靠软链接暴露。外部 Git 仓库优先用 submodule 固定 commit,并先拉一个验证位置正确再批量拉取。
1. **规划期验证本地可跑**:安装依赖,确认 `make grade`、`python grade.py` 一类入口能跑出结果。环境问题不留到学习期。
2. **连带抓取该 lab 的 handout 与必要框架说明**——lab 依赖所属课程的术语与代码框架,脱离上下文不可用。
3. **只有线上评测、没有本地测试的**:写一层薄的本地用例壳;做不到则降为自查清单。
4. **不抓取课程的 solutions / 参考答案**:检查点的约束力依赖答案不可见。这与下面"评测机先写后做"是同一条原则。
5. **拉取后立即验收**:`labs/` 顶层可见且不是软链接;每个作业至少有 README/handout、测试入口或明确的环境限制;submodule HEAD 可解析。没有通过就不报告“Lab 已拉取”。

### 2. 自建 lab(现成 lab 覆盖不了的缺口)

目录结构(可用脚本生成:`python scripts/learning_skill.py lab <repo> --name "名称"`):

```text
labs/labNN-<名称>/
  README.md      任务说明、输入输出约定、完成判据
  starter/       起始代码(可选)
  solution/      用户的解答
  judge/         评测机
```

评测机要求:

- 一条命令跑完(如 `python judge/run.py`),输出人和程序都能读的 PASS / FAIL。
- 覆盖边界用例;凡存在可对照的标准解,加随机数据 + 暴力参考解对拍(stress testing),比手挑用例可靠得多。
- **评测机在规划期写好并 commit**。临场现写的评测机会不自觉迁就用户已有的解法,先写后做才有约束力。
- **评测通过 ≠ 理解**。学习者提交且评测通过后,在同一次受邀检查内追问一个"为什么"级别的问题(复杂度的依据、某处设计取舍的原因),回答按 §8 锚定格式记入 dialogue。

### 3. 推导核对(可逐步核对的数学 / 理论)

逐步对照资料:每一步指明依据(定义、定理、资料位置);说不清依据的步骤记为薄弱点。不要对整个推导打"对 / 错",指出具体哪一步与资料不一致。

## qa 模式:自查清单

- 每个阶段附一份自查题 / 反思题清单,形态对齐目标判据:
  - 应试 → 对标真题难度的题目
  - 读懂论文 → 复述方法与结论 + 一个批判性问题(例:这个方法的前提在什么情况下不成立?)
  - 通识阅读 → 概念辨析与回到文本的指认题
- 清单在阶段开始时交付,此后不主持、不催、不追问完成情况。
- 学习者提交答案或主动要求核对时,按 SKILL.md §8 锚定格式对照资料核对。

## 间隔热身(仅 strong 模式)

距上次记录超过约两周时:汇报状态后,提议用记录中的薄弱点做 2-3 题回忆热身,并说明可拒绝。间隔后的提取练习对长期记忆收益最大,但选择权在用户。

qa 模式不提议热身,只汇报状态。
